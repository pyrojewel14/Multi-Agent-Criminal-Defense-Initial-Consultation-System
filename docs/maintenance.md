# 文档维护规范

本规范用于新增、改写、迁移和归档项目文档，以及代码变更后的文档同步。目标是保持明确的阅读入口、主题归属和证据范围，将维护安排在每次变更中。

## 新增前先判断

1. 从 [文档导航](README.md) 查找已有主题，阅读对应主说明。已有篇章能够承载内容时，优先修改该篇。
2. 新建长期文档须有独立的阅读目的，例如独立模块的使用说明或需要保留理由的设计决策。一次任务、一次验证或一次交付不自动成为新建长期文档的理由。
3. 确定公开、私有、临时或历史用途，再选择目录；同一主题的当前说明只维护一份。
4. 新文档必须进入所在主题或目录的导航，说明它与已有主说明的关系。目录调整须有明确的职责变化，不为单次任务另建一套分类。

## 目录与文件类型

| 类型 | 位置 | 维护方式 |
| --- | --- | --- |
| 当前公开技术说明 | `docs/`，已有主题子目录优先 | 直接更新正文，维护当前行为、使用方法和限制。 |
| 仓库级入口 | 根 `README.md`、已有贡献或操作入口 | 保持简短，技术细节链接到主说明。新建根目录文件须有仓库级用途。 |
| 私有个人材料 | `.private/interview/`、`.private/notes/`、`.private/codex/` | 分别维护面试表达、个人笔记与任务续接，不复制到公开仓。 |
| 临时工作材料 | `.scratch/<任务>/` | 按需使用 `scripts/`、`evidence/`、`snapshots/`；没有对应内容时不创建空目录。 |
| 公开历史说明 | `docs/history/`、已有 `evaluation/history/` | 明确日期、当时范围和当前替代入口，不作为现行操作说明。 |
| 私有历史记录 | 已有私有归档目录 | 保留设计理由、失败、原始证据和旧版本，导航中标明历史用途。 |

当前主题文件使用稳定名称；日期用于实验和历史记录。不要以“最新”“最终”“V2”等名称制造多份当前说明。迁移时同步入口和相对链接，保留旧路径到新路径的映射；原始日志中的当时路径不改写为今天的路径。

## 主题主说明与同步触发

主说明负责完整解释本主题。其他篇章只保留理解当前段落所需的摘要和链接；发现重复事实时，把完整内容集中到主说明。新独立主题建立主说明后，在本表补充职责与同步触发，不另建重复目录清单。

| 主题 | 主说明 | 需要核对的变化 |
| --- | --- | --- |
| 项目概览与阅读路线 | [项目首页](../README.md)、[文档导航](README.md) | 展示范围、主要能力、启动入口、文档增删或迁移。 |
| 安装与运行 | [安装说明](setup.md) | 依赖、启动命令、模型、索引、环境变量、部署配置。 |
| 组件与存储职责 | [架构](architecture.md) | 模块边界、执行权威、持久化、缓存、审计与一致性。 |
| 节点与状态流 | [工作流](workflow.md) | 状态字段、条件边、中断、恢复、人工动作。 |
| 接口与权限 | [API](api.md) | 路由、请求响应、错误、角色、鉴权和所有权。 |
| RAG 与覆盖概览 | [RAG](rag.md) | 候选来源、验证资格、要件与覆盖的关系。 |
| 法条资产与标注 | [全量刑法](knowledge/full_criminal_law.md) | 资产版本、数量、加载方式、标注资格与复核范围。 |
| 全量召回与排序 | [全量检索](knowledge/full_law_retrieval.md) | 召回、融合、重排、HyDE、设备与失败处理。 |
| 单案记忆与上下文 | [Memory](memory/README.md) | 原文、字段、摘要、游标、预算、回执和恢复边界。 |
| LawRef 响应协议 | [协议诊断](knowledge/lawref_response_protocol.md) | 模型输出契约、供应商通道、提示词与受限对照。 |
| 测试组织 | [测试](testing.md) | 测试分组、命令、替身和 CI 对应范围。 |
| 评测口径与执行 | [评估说明](evaluation.md)、[执行入口](../evaluation/README.md) | 前者负责数据契约与指标解释，后者负责执行命令和结果位置。 |
| 能力边界 | [限制说明](limitations.md) | 新证据、失败、已知缺口和可证明范围发生变化。 |

代码、配置或数据变更影响上述行为时，在同一批变更中核对相关主说明及引用它的摘要。只改受影响内容；文档同步不要求重写所有篇章或自动重跑全部实验。私有续接、面试或演示材料需要引用变化时，同步摘要与证据范围，技术细节仍指向公开主说明。

## 改写与证据

- 当前说明直接修正正文，删去已被替代的当前判断，不在末尾不断追加按日期排列的任务进展。需要保留的旧理由或结果转为历史记录，并留下替代入口。
- 当前技术说明写清用途、适用范围、实际入口、使用方式和已知限制。核对重要事实时指出相关源码或配置；日期和提交标识用于需要固定版本的事实或证据，无须为纯措辞调整刷新整篇核对日期。
- 区分源码存在、工作区实现、已提交版本、定向测试、真实运行和独立验收。文件存在、schema 合法、测试通过、模型响应和完整业务效果分别有自己的证明范围。
- 实验记录写明日期、版本或工作区状态、配置、命令、样例及分母、结果、失败和原始证据入口。本次没有执行的检查，不写成本次通过；保留失败和不可比条件。
- 原始日志、评测 JSON、数据库快照和历史附件保留原字节。解释或更正写在独立说明中；确需重生成时产生新记录，不能覆盖旧证据并沿用旧日期。
- 不把任务建议写成用户授权，也不把子任务交付写成主线程验收。私有当前状态与问题清单分别维护续接信息和未决事项，不复制完整任务日志。

新增或实质改写当前说明时，可按以下结构组织；没有对应内容的段落可以省略，保持已有合理结构：

```markdown
# 主题名称

说明读者用本页解决什么问题，以及适用范围。

## 当前行为
解释职责、流程与必要术语，并指向关键源码或配置。

## 使用与配置
提供项目通用命令和仓库相对路径。

## 验证与边界
区分已核对事实、实际运行证据与仍待验证的部分。

## 延伸阅读
链接相关主说明、执行入口或必要历史记录。
```

## 公开与私有边界

公开文档、Issue、PR、评论和附件不得包含本机用户名、机器名、个人绝对路径、本地环境名称、本机专属配置或私有材料。公开复现使用项目通用命令和仓库相对路径；本地执行要求保留在私有规则中。

公开页面不得链接到私有仓或临时目录。需要公开证据时，先明确可公开的范围，再建立公开可访问的证据入口；不能直接复制私有报告。私有材料可以链接公开技术说明。

## 每次变更的收尾

完成前按实际变更核对以下项目：

- 新增是否确有独立用途，内容是否已有主说明，目录和文件名是否稳定。
- 新增、删除、改名与标题变化是否同步导航、引用和锚点；相对链接是否从所在文档位置解析。
- 当前事实是否符合源码或配置，版本状态是否准确，实验数字是否保留日期、分母与证据范围。
- 公开内容是否夹带本地或私有信息，私有与临时内容是否仍在各自边界内。
- 相关仓库的 `git diff --check` 是否通过；新增未跟踪文档还需单独检查正文与链接。

链接或信息检查工具可用时执行，并核对真实输出；工具不可用时人工检查本次范围，明确检查方式和限制。上述规则目前不代表已有自动 CI 门禁，也不能用本次整理专用的旧文件哈希基线检查日常代码变更。

任务结束时，报告受影响的文档与检查范围；无需更新文档时说明理由。临时产物按任务保留，必要结论提炼进主说明，不默认新增永久“完成报告”。有价值或用途不确定的材料保留；删除、跨公开私有边界迁移和发布仍按当前授权处理。
